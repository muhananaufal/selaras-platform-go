Lapisan 1
Cerita: sehari bersama Selaras Satu reel, sembilan adegan, tanpa satu pun kotak infrastruktur di layar.

C

Sehari bersama Selaras

Satu pengguna, satu hari, dari mendaftar sampai (pilihan) menghapus akun. Tiap adegan memperlihatkan layar yang ia lihat, apa yang ia tunggu, dan berapa lama.
belum

Komponen di kanvas

  • Satu ponsel besar di tengah dengan layar yang berganti (mockup: formulir, kartu risiko, daftar tugas, chat, menu, dasbor)
  • Satu sosok "sistem" di kanan yang hanya berdenyut saat bekerja, tanpa nama komponen
  • Garis waktu pengguna di bawah: "menunggu X ms" vs "datang belakangan"

Adegan (bab)

  1. Mendaftar, atau masuk lewat Google; profil kesehatan diisi
  2. Kuesioner risiko: angka dan kategori muncul seketika
  3. Minta laporan personal: tiket dulu, laporan menyusul (notifikasi)
  4. Mulai program coaching; kurikulum datang belakangan; tugas hari ini
  5. Bertanya ke pelatih di dalam program
  6. Bertanya bebas ke asisten
  7. Panduan menu hari ini sesuai preferensi dan bahasa
  8. Dasbor: semua kemajuan hari ini di satu layar
  9. Menghapus akun: konfirmasi kata sandi, "sedang diproses", lalu semuanya hilang

Bisikan "di balik layar"

  • Satu kalimat per adegan, muncul kecil di bawah ponsel: "laporan dibuat pekerja di belakang, bukan saat kamu menunggu"
  • Setiap bisikan menaut ke alur lapisan 2 yang relevan

Cabang

  • Laporan gagal dibuat: pengguna melihat "gagal, coba lagi", bukan menunggu selamanya
  • Tiket kedaluwarsa saat pindah perangkat: diminta masuk lagi (satu sesi aktif)

01

Daftar, masuk, dan sesi

Akun lahir, profil kosong dibuat dengan token bootstrap, token diverifikasi gateway sendiri, sesi lama mati saat masuk lagi.
berikutnya

Komponen

  • klien, edge-gateway, Redis, identity-svc, profile-svc, Postgres (svc_identity, svc_profile), Mailpit, Google

Bab dan langkah

  1. POST /register → rate limit IP → argon2id → INSERT users → CreateEmptyProfile dengan token bootstrap 30 s → token EdDSA (gen 1)
  2. GET /me → tanda tangan lokal → generasi di Redis (cache kosong → identity) → 200
  3. POST /login dari perangkat lain → hash umpan untuk alamat tak ada → generation++ → publish ke Redis → token lama mati
  4. POST /logout → generation++ → 401 untuk token lama
  5. Reset kata sandi lewat Mailpit (jawaban seragam anti-enumerasi); masuk lewat Google dengan state wajib

Cabang

  • Redis mati saat memeriksa generasi → tanya identity; identity ikut mati → 503 gagal-tertutup, bukan 401
  • gRPC langsung ke profile-svc tanpa token → Unauthenticated; token orang lain → PermissionDenied
  • Profil kosong gagal dibuat → pendaftaran tetap sukses, dicatat sebagai peringatan

M1

Transactional outbox dan relay

Kenapa event ditulis di tabel yang sama dengan datanya, dan kenapa relay memilih duplikat daripada kehilangan.
berikutnya

Kanvas

  • Satu transaksi bisnis, tabel data, tabel outbox (id, event_type, aggregate_id, status), proses relay, satu partisi Kafka

Langkah (per pernyataan)

  1. BEGIN; UPDATE data; INSERT outbox; COMMIT (penulis event dibangun DARI transaksi, bukan dari kolam)
  2. Relay: BEGIN; SELECT … WHERE published_at IS NULL FOR UPDATE SKIP LOCKED
  3. TopicFor(event_type); yang tidak bisa dirutekan ditandai gagal supaya tidak dibaca selamanya
  4. Publish dengan acks=all + idempoten, dibatasi PublishTimeout, di luar transaksi
  5. MarkPublished untuk yang terkirim; galat publish ditelan dengan sengaja supaya tanda terkirim tidak batal
  6. COMMIT relay

Cabang kegagalan

  • Mati sebelum COMMIT bisnis → tidak ada data, tidak ada event
  • Mati setelah publish, sebelum mark → dikirim ulang → duplikat (ditangani M2), bukan hilang
  • Dua relay bersamaan → SKIP LOCKED memisahkan barisnya
  • Broker mati → baris pending menumpuk lalu mengalir
  • Tanda terkirim ditulis dulu (alternatif yang ditolak) → event hilang selamanya
